Die Akteure

Drei Rollen, klare Verantwortung

Jede Rolle hat fest definierte Befugnisse. Keiner überschreitet seinen Bereich.

Sonnet

Der Implementierer

  • Schreibt allen Code
  • Erstellt Unit-, Integrations- & E2E-Tests
  • Führt Build, Lint, Tests aus
  • Macht Git-Commits
  • Aktualisiert Artefakte
Opus

Der Architekt & Prüfer

  • Plant Implementierungen (Phase 2.5)
  • Definiert Architektur-Entscheidungen
  • Security Reviews bei Auth/API
  • Validiert fertige REQs (Validator Loop)
  • Schreibt keinen Code
loop.sh

Der Orchestrator

  • Startet Iterationen automatisch
  • Injiziert Kontext + nächstes REQ
  • Trackt Kosten, Dauer, Tool-Calls
  • Crash Recovery & Rollback
  • Löst Validierungen aus
Wissensbasis

7 lebende Dokumente

Jede Iteration liest und schreibt spezifische Dokumente. So bleibt Wissen über Sessions hinweg erhalten.

PRD.md

Requirements mit Status, Priorität, Größe, Abhängigkeiten und Akzeptanzkriterien. Wird jede Iteration gelesen, Status aktualisiert.

status.json

Autoritative Statusquelle. Maschinenlesbar. Wird zuletzt geschrieben (nach Git-Commit) um Korruption zu vermeiden.

context.md

Kurzer Projektkontext (max 50 Zeilen). Wird jede Iteration komplett neu geschrieben. Enthält: was existiert, was als nächstes kommt.

architecture.md

Architektur-Entscheidungen als ADRs. Append-only — bestehende Einträge werden nie geändert oder gelöscht.

learnings.md

Persistente Erkenntnisse aus früheren Iterationen. Append-only. Bugs, Workarounds, Muster die nicht vergessen werden dürfen.

AGENT.md & VALIDATOR.md

Geschützte Instruktions-Dateien. Der Agent darf sie nicht verändern. Definieren Phasen, Regeln, Ablauf.

Phase 2

Preflight

Bevor Code geschrieben wird: Ist die Umgebung gesund?

1
Projektstruktur
Verzeichnisse, node_modules, package.json vorhanden?
2
Build
npm run build muss erfolgreich durchlaufen
3
Tests
Alle bestehenden Tests müssen grün sein
4
Linter
Keine ESLint-Fehler (Warnungen ok)
5
Playwright MCP (IMMER Pflicht)
Browser-Verifikation muss erreichbar sein. Ohne Playwright → sofort blocked.
6

PocketBase + Nginx müssen laufen (entfällt bei SANDBOX_MODE)

Preflight-Failure? — Regressions-Check: War es die letzte Iteration? Fix oder Rollback. Nie implementieren auf kaputtem Fundament.

Phase 2.5 — Nur für M-REQs

Opus plant, Sonnet setzt um

Für mittelgroße Requirements erstellt Opus einen verbindlichen Implementierungsplan.

Was Opus bekommt

  • Vollen Codebase-Zugriff (liest selbst)
  • context.md, architecture.md, learnings.md
  • Akzeptanzkriterien des REQs
  • Pfade relevanter bestehender Dateien

Was Opus liefert

  • Welche Dateien erstellen/ändern (exakte Pfade)
  • Welche Patterns & Signaturen verwenden
  • Welche Tests schreiben
  • Neue Architektur-Entscheidungen (ADRs)
  • User Journeys für den Smoke-Test

Opus' Plan ist verbindlich.
Sonnet weicht nur ab wenn technisch unmöglich.

Phase 3

Implement

Sonnet schreibt Code, Tests und einen Sicherheits-Checkpoint-Commit.

Code

Implementierung gemäß Opus-Plan. Status in PRD.md auf in_progress. Akzeptanzkriterien abhaken.

Tests

Unit-Tests (Vitest), E2E-Tests (Playwright). Mocks nur für externe APIs — eigene Module werden real getestet.

Checkpoint

WIP-Commit als Sicherheitsnetz. Bei Timeout geht keine Arbeit verloren. Kein git add -A!

Test-Ebene Tool Mock-Regeln
Unit Vitest + React Testing Library PocketBase SDK, fetch, localStorage — OK
Integration Vitest + echte Module Eigene Module NICHT mocken
E2E Playwright Kein Mocking — echte App im Browser
Smoke Playwright MCP Echte App + Docker Stack
Phase 4

Verify

Mehrstufige Verifikation. Kein done ohne bestandenen Smoke-Test.

4.1
Build + Tests + Lint
Automatisierte Checks müssen alle grün sein
4.1b
Akzeptanzkriterien-Gate
Jedes Kriterium einzeln abgehakt? Sonst kein done.
4.2a
Core-App-Smoke-Test (PFLICHT)
App im Browser öffnen. Kein Crash. Keine Console-Errors. Navigation funktioniert.
4.2b
REQ-spezifische User Journeys
Von Opus definierte Szenarien durchspielen
4.3
Full Verification (alle 3 Iterationen)
Responsive, Accessibility, visuelle Prüfung

Kardinalregel

Teste wie ein ECHTER Nutzer

  • Kein internes Wissen verwenden
  • Bei jedem Feld fragen: "Wüsste ein Nutzer das?"
  • UX-Bugs melden statt umgehen
  • Nicht nur den Happy-Path testen

Kein done ohne Playwright-Smoke-Test. Keine Ausnahmen.

Phase 5

Persist

Ergebnisse sichern. Die Schreibreihenfolge ist kritisch.

Atomare Schreibreihenfolge

1. Artefakte aktualisieren

context.md neu schreiben, learnings.md + architecture.md appenden

2. PRD.md updaten

Status auf done, Checkboxen abhaken (best-effort)

3. Git Commit (ohne status.json!)

Code + Artefakte committen. Kein --amend.

4. status.json finalisieren (LETZTER Schritt)

Erst nach dem Commit. Atomic Write (temp + mv). Bei Crash/Timeout bleibt das REQ auf in_progress statt fälschlich done.

5. Status-Block ausgeben

Maschinenlesbarer Block für loop.sh (REQ, Status, Metriken)

Qualitätssicherung

Der Opus Validation Loop

Alle 5 Iterationen prüft Opus die Arbeit von Sonnet. Opus schreibt keinen Code — es validiert und korrigiert.

Was Opus prüft

Akzeptanzkriterien

Jedes einzelne Kriterium gegen Code verifiziert

Echte Playwright-Smoke-Tests

App im Browser öffnen, klicken, prüfen

Log-Analyse

Regel-Umgehungen? Tests übersprungen? Mocks-Missbrauch?

Security Review

Bei Auth/API-REQs: XSS, Injection, Auth-Bypass

Korrekturen

REQ zurücksetzen

done → open (Sonnet muss nacharbeiten)

REQ blocken

Bei fundamentalen Problemen

Learnings dokumentieren

Muster für zukünftige Iterationen festhalten

Dynamisches Intervall:
Alles sauber? → Nächste Prüfung in 5 Iterationen
Korrekturen nötig? → Nächste Prüfung in 3 Iterationen

Robustheit

Sicherheitsnetze

Autonome Agenten scheitern. Das System ist darauf ausgelegt.

Crash Recovery

In-progress REQs werden automatisch auf open zurückgesetzt. WIP-Checkpoint-Commits überleben Abstürze. status.json-Backup vor jeder Iteration.

Repeat Detection

Gleiches REQ 3x hintereinander versucht? Automatisch blocked. Endlos-Schleifen vermeiden.

Timeout & Turn-Budget

30 Min. pro Iteration. 100 Turns pro Agent-Session. Ab Turn 80: nur noch abschließen. 2x Low-Activity? Loop stoppt automatisch.

Scope Guard

Geschützte Dateien: AGENT.md, VALIDATOR.md, loop.sh, CLAUDE.md. Der Agent darf sie lesen, aber nie verändern.

Cost Tracking

Kosten pro Iteration & kumuliert. Token-Breakdown pro Modell (Opus, Sonnet, Haiku). JSONL-Log für spätere Analyse.

Git Tags & Branches

Automatischer Agent-Branch (nicht auf main). Tags pro Iteration für Rollback. Kein force-push, kein amend.
